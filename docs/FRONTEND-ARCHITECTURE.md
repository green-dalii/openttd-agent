# 前端架构：维护成本的来源与四条结构改造

> **职责**：本文件回答"手写前端以后会不会越来越贵"，并给出**可执行的改造顺序与验收**。
> **边界**：构建链/第三方库取舍在 `docs/FRONTEND-LIBRARY-EVALUATION.md`；UnoCSS 专门评估在
> `docs/UNOCSS-MIGRATION-PLAN.md`；页面与 API 形状在 `docs/DASHBOARD-UI.md`、
> `docs/DASHBOARD-API.md`；开发准则在 `AGENTS.md`（本文件只给**做法**，不复述准则）。

## 1. 先把问题说准（用事实，不用印象）

近几周前端出的问题**不是**"裸写 JS 所以难" —— 逐条看它们的**根因类型**：

| 事故 | 根因类型 | 框架能防住吗 |
|------|----------|--------------|
| `/evolution` 导航跑到右边（2026-09-25） | **同一结构有 4 份副本**，其中一份结构写错 | 不能（4 份手写 header 在任何框架里都能漂移） |
| 线路面板空、城镇面板空（2026-09-23/25） | **后端有数据、却从没发到页面**（`routes`、`towns`） | 不能 |
| 步骤表每帧 1.8k–2.6k 次 DOM 变更 | **数据量与推送率**（不是框架慢） | 不能 |
| "0 控制台错误"却是假的（D45/D51/D53） | **验证方法**（空状态、漏条件、错选择器） | 不能 |
| `null` 被渲染成 `0`（今天，被单测抓住） | **诚实规则**没被锁住 | 不能 |

**结论**：真正的成本来自**同一个行为要改几处、以及改错时是否静默**。
框架不改变这两件事；**结构**改变。因此先做结构，不先换框架。

规模（2026-09-25）：5 个页面、前端 JS+HTML ≈ 7.3k 行；最大文件
`live-view.js` 47 KB、`ucharts.js` 44 KB、`common.js` 31 KB、`live.js` 20 KB。

## 2. 四条结构改造（按性价比排序，各自可独立验收）

### S1 页头/导航：**一个来源** ✅ 已完成（2026-09-25）
页面只声明 `<div class="brand" data-brand="live"></div>`，内容由 `common.js` 的
`renderChrome()` 生成；守卫 `test/unit/web-assets.test.ts` 断言"任何页面不得手写 `<h1>`/`<nav>`"。
**验收**：往任一页面重新手写标题或导航 → 测试红。

### S2 快照契约：**一份类型 + 一处转换 + 一处校验**
- 后端：`toWireSnapshot()` 是快照的**唯一**转换点（已有，且它的注释记录了"两份实现漂移"的历史）。
- 前端：`live.js` 的 `onSnapshot` 是**唯一**入口，逐字段显式映射（现状）。
- **缺的那块**：字段名两端都是**手写字符串**，所以"后端加了字段、前端没接"能静默通过
  （今天就是靠**人工**才发现 `towns` 没发出去）。
- 做法：把快照形状提升为一处**类型声明**（`src/types.ts` 或 `wire-snapshot.ts` 导出
  `WireSnapshot`），前端消费处用 `JSDoc @type` 引用；再加一条**开发期形状检查**
  （`assertSnapshotShape()`，仅在 `NODE_ENV !== "production"` 或 `--dev` 下运行）：
  页面拿到未知/缺失字段时 `console.warn` 一次（不是每帧）。
- **验收**：① 在 `toWireSnapshot` 里加一个字段但不接前端 → 有测试/警告指出；
  ② 前端读取不存在的字段 → 运行时给出**一次**警告（而不是静默 `undefined`）。

### S3 视图模型：规则留在纯函数里，模板只做字段访问
现状已在这么做（`*-view.js` + 单测），但**没有强制**：
- 规则：**模板里不做推导**（`x-text` 只允许"字段/方法调用"，不允许三元套三元）；
  任何"给什么状态 → 显示什么"的判断都进 `<page>-view.js`，并**必须**有单测。
- 收益已被证明：今天的 `Number(null) === 0`（未知总数被显示成"0 个城镇"）
  就是被 view model 的单测抓住的；而它若写在模板里，只会表现为"数字看起来有点怪"。
- **验收**：新增/修改页面规则时必须同时出现 `<page>-view.test.ts` 的用例；
  lint 层可逐步收紧（例如禁止模板里出现 `?` 嵌套）。

### S4 组件词汇：把重复的 5 种结构变成"可复用 + 可看"
重复出现的结构：`kpi` 卡、`panel`（标题+空态+表格）、`kv` 表、空态行、抽屉。
- 做法：`common.js` 已有 `kpi()` 这类构建器 → 补齐 `panel({title, note, empty, body})`；
  再做一个**开发者目录页** `/dev/components`（只在 `--dev` 下路由），把每种结构在
  "有数据 / 无数据 / 不可得"三种状态下**渲染出来**，供人工看。
- 为什么值得：本项目**反复**在"空态与不可得态"上出错（D50：加了状态却没给退场；
  `routesAvailable`/`townsAvailable` 都是后补的）。把三种状态**并排展示**，
  是把"漏一个状态"从"靠人记得"变成"一眼看得见"。
- **验收**：新页面不再出现新的 `<table class="kv">` 手写副本；目录页覆盖三种状态。

## 3. 为什么不现在换框架（含何时该换）

| 方案 | 现在换的代价 | 现在换的收益 | 判定 |
|------|--------------|--------------|------|
| **保持 Alpine + 原生，做 S1–S4** | 低（增量） | 直接消灭本次事故的两类根因 | ✅ **推荐** |
| **Preact + htm**（无构建链，8 KB + <600 B） | 5 个页面重写；已有 41 个前端单测要重做 | 组件模型更硬，但本项目**没有**"组件组合爆炸"的证据 | ⏸ 暂缓 |
| **Svelte/Vue（需构建链）** | 引入工具链 + 产物陈旧面；违反 D3(b) | 同上 | ⏸ 暂缓（需所有者先改 D3） |
| **UnoCSS / Web Awesome** | 见 `docs/UNOCSS-MIGRATION-PLAN.md` | 与"结构"无关 | ⏸ 见该文档结论 |

**换框架的触发条件（事先写清，避免拍脑袋）**：当同一类**结构性问题**在 S1–S4 之后
仍重复出现 ≥2 次，且它的根因被归到"状态管理与组件复用"（而不是"少一处来源"或"少一条验证"）时，
再评估 Preact+htm 这类**无构建链**方案。

## 4. 新页面的完成定义（与 `AGENTS.md` §7 一致）

1. 页面只声明 `data-brand`，页头/导航由 `renderChrome()` 生成（S1）。
2. 该页的状态与规则集中在 `<page>-view.js`，并有单测（S3）。
3. 消费的快照字段来自**类型化**的 `WireSnapshot`（S2）。
4. 每个面板都明确"有数据 / 无数据 / 不可得"三种状态的显示（S4）。
5. `pnpm run gate` + `pnpm run dashboard:smoke` 绿；`dashboard:smoke` 里为该面板加一条断言
   （**守卫必须在循环里**，见 MEMORY D49）。
