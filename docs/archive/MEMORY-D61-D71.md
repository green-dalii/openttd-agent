### D61 —— 通路 ≠ 效果（2026-09-26 审计）

**现象**：记忆注入、反思、`recall` 全部建好且真机被调用过（`recallCalls=2`）。直觉上"经验回路在工作"。但唯一有效对照（§10.42）：**记忆无收益**。"通道活着"与"学习发生"之间没有任何被测量的桥。

**根因**：工程完成度给人"有效"的错觉。D4 守住了"不能给 control 臂泄漏"，
但没有人守住反方向：**不得把"用过"写成"有用"**。

**规则**：凡声称"某机制让 agent 变强"，必须给出预登记的统计（趋势斜率 CI / 对照效应）
或明确写「该设计下不可判定 + 需要 n」。`recallCalls>0`、lessons 数量、注入次数
都是**过程量**，不是**结果量**。汇报时分开两类数字。

### D62 —— 门禁的覆盖面本身要有守卫（2026-09-26）

**现象**：`tsconfig.json` 的 include 只有 `src/**` + `test/**`。`scripts/*.ts` 不在
type 门禁内。`scripts/run-experiment.ts`——**实验判据脚本**——长期带 25 个真 TS 错误
（`view.arms` unknown、`Args.vary` 不存在），而 `pnpm run gate` 一直是绿的。

**根因**：D49 说"守卫存在 ≠ 守卫在循环里"，这条是同一族的另一面：
**守卫的覆盖面退化了也没人知道**。新目录（`scripts/`）落到了所有 tsc 项目之外，
门禁绿灯继续为一个没被检查的角落背书。

**规则**：仓库里每个 `*.ts` 必须被某个 tsc 项目覆盖；用**静态守卫**锁住
（扫描 tsconfig 的 include/exclude 或直接 `tsc --noEmit` 逐项目跑）。
判据/实验脚本与产品代码同权——它们出错时，错的是**结论**。

### D63 —— "重建对象"是丢字段的惯犯：D55 第三次（2026-10-07）

**现象**：城镇名在 GS 载荷里、hub 解析了、类型也带了——但页面仍显示 `#4`。
真凶是 `WorldState.setTowns` 里的 `.map()`：它**重建**对象，只挑 `id/population/x/y/cargo`，
`name` 死在这最后一公里。同一功能里（towns 面板）这个家族的坑已是第三次。

**根因**：凡"把外部对象重塑成内部形状"的 `map/rebuild`，就是**静默过滤器**——
加字段的人改了生产端与解析端，却不知道中间还有一个挑选字段的重塑层。
测试也没抓到：单测直接喂 `model.towns`（绕过了重塑层）。

**规则**：每个重塑层配一条**字段透传测试**（喂全字段 → 断言逐字段出现在输出）；
新字段的验收必须是"它到页面并被渲染"（D55 原句，这次是严格执行版）。

### D64 —— 协议文档的"应然"是假设：等 ServerProtocol 再 JOIN 直接死锁（2026-10-07）

**现象**：admin 握手抖动（ECONNRESET / `'' has disconnected` / `write EPIPE`）。
我按协议文档的"应然"顺序改（服务端先发 PROTOCOL、客户端后 JOIN）并写了锁顺序的测试。
结果真机**死锁**：裸 socket 实测——连上后空等 3 s **零字节**，这个 OpenTTD 15.3 是
**"先收后说"**：客户端不先发字节，PROTOCOL 永远不来。

**根因**：把协议文档的顺序当成了事实。文档写的是协议设计；实现可以不合设计。
我的测试把假设固化成了规范——若带着它发布，就把一个能用的客户端改成了永连不上。

**规则**：协议顺序、握手时序这类"应然"，动手前先用**最小裸探针**（一个 socket、
几行脚本）对真机量一次；测试锁**实测行为**并把实测口径写进注释。
配套：自举窗口竞态的修法是**有界重试到握手完成**（`connectAuthed`），
不是加大超时。


### D65 —— 「没找到」的分母错了就是捏造（2026-10-08）

P1-1b 要给 GS 找回 `pathfinder.road`。我先查 `/Applications/OpenTTD.app`，报告「app bundle 里没有库」——**但游戏二进制在 Steam 目录**（`src/config.ts` 的候选列表第一个就是），我查了个空目录。真实的库一直躺在 `~/Documents/OpenTTD/content_download/ai/library/`（内容包，与 BaNaNaS 发布版字节一致）。

同族陷阱两个：① 改名守卫正则 `\bAI[A-Z][A-Za-z]*\b` 匹配不到 `AIBridgeList_Length`（下划线是词字符，`\b` 卡住）——守卫全绿但漏了真实残留，真机才炸出来；② 兜底式 `AI→GS` 批量替换把补丁声明文字里的**原名**也改掉了，GPL 溯源被抹，守卫再抓一次。

**规则**：① 证据性「不存在」结论必须写明「我在哪找的、为什么那里该有」——两个出处缺一，就是分母没验；② 标识符匹配一律 `\w*`（含下划线/数字），改名类守卫先用一个已知应命中样本自证会失败；③ 批量替换后必须重写引用原名的溯源文字。


### D66 —— 早退 return 吃掉了维护循环（2026-10-08）

P1-1 端口的 `Tick`：施工队列空 → `return`。尾部的 `CheckAddVehicles`/`ProcessFleetSells`/`CheckRetireRequests` 于是只在**施工中**跑。done 后的 `set_route_vehicles`/`retire_route` 全部入队、有回执、永不生效——正是 「通路 ≠ 效果」（D61）的又一实例，而这次是**我自己端口时引入**的。

**规则**：① 维护性循环不要挂在可能早退的主路径后面；早退分支必须同样做维护，或在注释里显式声明「此处不做 X」；② 有回执的请求类协议必须配**生效侧**的观测（具名 phase 带计数），否则「收到请求」会冒充「完成请求」；③ 此类缺陷的最小暴露法是真机 Phase 序列对照（请求相位有、应用相位无 = 断链）。

### D68 —— 门禁的退出码被管道吃掉（2026-10-08）

**现象**：文档工作做完跑 `pnpm run gate 2>&1 | grep -E "Tests |FAIL" && git add -A && git commit`，
输出里明明有 `FAIL test/unit/process-manager.test.ts`，**提交照样成功了**。

**根因**：管道的退出码取**最后一个命令**（`grep`）的，`grep` 找到了 `Tests` 行 ⇒ 退出码 0。
真正的门禁码被丢掉了。`AGENTS.md` §2 写的是"红=停"，但我的执行方式让"红"不可见。

**附带发现**：门禁的 `lint` 脚本原本是 `eslint .`（无 `--max-warnings`）⇒ **warning 永远不失败**（pre-commit 钩子用的是 `--max-warnings 0`，所以只有钩子能抓到）。已改为 `eslint . --max-warnings 0`：门禁对 warning 必须有反应，否则警告只是装饰。

**规则**：① 门禁判定**只看门禁自己的退出码**——`pnpm run gate > .scratch/gate.log 2>&1; echo "gate=$?"`，
再单独 grep 日志里的失败项；② 提交前若门禁里有任何 FAIL，**先修再提交**；
③ "门禁绿"这个结论必须来自那条命令的码，不是来自"输出看起来没问题"。

### D69 —— 同一主题多份文档互相引用，就是漂移机制（2026-10-08）

**现象**：`docs/` 17 份 3121 行里，"前端怎么做"占了 4 份（依赖审计 / 库评估 / UnoCSS 计划 /
前端架构），"harness 给 agent 什么"占了 2 份（信号架构 / 脚手架契约），它们互相引用成环。
后果不是"读起来费劲"，而是**改一处必漏另一处**，且两份都能自洽地引用对方 ⇒ 没人发现漂移。

**根因**：文档按**写作时刻**切分，而不是按**主题**切分；每写一份新文档就用"指针"去接旧的，
而不是问"这个主题的权威应该是哪一份"。

**规则**：① 发现同一主题有两份文档 ⇒ **合并**（一份权威，其余进 `docs/archive/` 并加冻结横幅），
不交叉引用；② `docs/README.md` 是**地图**：每份文档写清"只回答什么问题/权威于什么/不含什么"，
新增文档必须登记，有守卫把它变成红（`test/unit/repo-hygiene.test.ts`）；③ 计划类内容不进 docs，
进 `ROADMAP.md`（未完成）或 `CHANGELOG.md`（已完成）。

### D70 —— 固定 sleep 等子进程 = 给门禁埋雷（2026-10-08）

**现象**：`test/unit/process-manager.test.ts` 的"tracks child exit and exposes log tail"
用 `setTimeout(800)` 等子进程退出。单跑必过，**全量并发时偶发红**（本次 gate 就撞上一次）。

**根因**：800ms 是"通常够"的估计，不是"已发生"的条件；机器一忙，子进程还没被回收，
断言 `isRunning()===false` 就失败。这类测试的失败**与被测代码无关**，却会消耗真门禁的信用——
门禁天天随机红，团队就会习惯性忽略它（比没有门禁更糟）。

**规则**：① 等待**条件**而不是**时长**：轮询到 `isRunning()===false`（带上限超时）；
② 新增涉及进程/IO 的测试不许写固定 sleep 当同步手段；③ 门禁出现偶发红时，
**先确认是测试抖动还是真缺陷**（单跑 + 复跑），再决定修哪边——不要把抖动当"环境问题"放过去。

### D71 —— 文档膨胀的机制是"默认允许只增不减"（2026-10-23）

**现象**：`SPEC.md` 有 **118 条 `### 10.x`**（每条一个"事实"，实际是每阶段的变更记录），
`ROADMAP.md` **654 行**里大半是已完成叙事（旧的 A/B 结果、冻结判定、compact 交接手册）。
两个文件都违反了 `AGENTS.md` §9 的职责表：SPEC 成了第二份变更日志，ROADMAP 成了历史档案。

**根因**：不是"谁写错了"，而是**默认允许只增不减**：① 每完成一个阶段就往 SPEC 追加一条 §10.x（"记录"压过了"归位"）；② ROADMAP 的历史章节删不掉——因为它们"还有用"（里面的确还藏着未完成项）；③ 没有守卫，于是"暂时多写一点"变成"永久多一份"。

**另一半的代价（本次实测）**：为合并 CHANGELOG 的三条 D1 条目写脚本切片，**误删了整个 Unreleased 段（1219 行）**——"用脚本改大段文档"和"手写"的风险面完全不同。恢复靠 `git checkout HEAD -- CHANGELOG.md` 再逐块改。⇒ **改大段文档必须先看 diff**。

**规则**：
① **一个阶段最多给 SPEC 一条**；实施流水进 CHANGELOG；新事实**归入已有主题**并登记进 §10 索引。
② **ROADMAP 只留未完成**（行数预算 + 不得出现"历史/已解决/完成史"章节）；删历史章节前，
   **先把里面藏着的未完成项捞出来列进待办**（本次捞出 11 条）。
③ **规则要落在守卫里**（AGENTS §9.1a + `repo-hygiene.test.ts`）：SPEC 条目必须登记、条目数有
   上限、ROADMAP 行数有上限——否则纪律会随时间失效。
④ **改大段文档前先看 diff**：脚本切片更容易误删；删完逐条查"删除行里有没有未完成项"，并修掉指向被删章节的指针（本次 6 处）。
