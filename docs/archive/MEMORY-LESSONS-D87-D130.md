### D90（2026-11-01）模板读的字段如果**没人写**，它会安静地显示 "—"
**现象**：Run 顶栏的 Elapsed 在运行中也永远 "—"；把 Session 移到页内后同样是 "—"。**根因**：`live-view.js` 声明了 `startedAt` / `sessionId`（注释还写"由 live.js 灌入"），**全前端没有一处赋过值**；`get elapsed()` 读 `this.startedAt`，而 `{...model}` 展开时 getter 已被求值 ⇒ 恒 "—"。**规则**：① 模板读的状态字段必须能指到**唯一写入点**，或由服务端字段派生（本例：`run.startedAt` / `telemetry.startedAt`）；② 运行态验收要断言字段**真的在变**（两次采样不同值），"不是 —" 可能只是偶然对齐；③ **空值既是诚实的也可能是死代码**——屏幕上长得一样，只能靠断言区分。
### D95（2026-11-05）Squirrel 的表/类是**严格**的：写不存在的键抛，**读不存在的键也抛**
**现象**：推送事件（Issue #13 S7d）接上后，GS 收到了 `station_first_vehicle`（真机探针：

### D114（2026-11-10）**「验证过 N 局」的闸必须数局，不能数采样**：一局可以记多条模式
**现象**：真机 500 日的一局里模型记了 5 条同模式采样 ⇒ 候选卡里有 **3 个读数**而只有 **1 个来源局** ⇒ 旧实现把**读数个数**当成"已验证局数"⇒ **单局三条高值采样就能过晋升闸**（SPEC §5.3 的"已验证局≥2"从未被强制）。同一局还暴露了第二个漂移：货运 F3 把 `build_freight_route` 加进了词表，但 `record_strategy` 的**描述**里没写它 ⇒ 模型把 5 条采样里的 **4 条**记成 `build_bus_route` ⇒ 同一个想法被拆成两张卡。

### D116（2026-11-11）**同一个概念只能有一处实现**：六份日历投影 = 六个各自漂移的时钟
**现象**：把日历日期换成"游戏日"的代码被**抄了六份**（`payload-parsers`/`signal-hub`/`runner-helpers`/`v02-runner`×2/`world-state`），而且抄的是**虚构的 360 天年**（`year*360 + (month-1)*30 + (day-1)`）⇒ 每年丢 5 天（1 月 31 日与 2 月 1 日同号）⇒ "250 游戏日"实际约 256 **日历**天；季度又按"天数 / 90"推（而日历年里的季度是 90–92 天）；线路"每日收益"的分母用 `gameDate % 365`（不是年内第几天，且与分子年份不同步）。**六份都不报错**。
**根因**：换算逻辑是"一行算术"，看起来不值得抽函数 ⇒ 每处各写一遍 ⇒ 改一处不会改别处 ⇒ 而且每一份都可能与**被量的那个量**脱节（分子来自引擎、分母来自想象）。
**规则**：① **换算要有唯一出处**（本项目：`src/game/calendar.ts`），任何新调用点 import 它，不许复制；② 抽出来的实现要**能被静态守卫锁住**（`test/unit/calendar-guard.test.ts`：360 只许出现在这一个文件）；③ 凡是自己算出来的"时间单位"，先问**它和引擎的单位是同一个吗**（日历 vs 引擎年 vs 墙钟）；④ 抄写六份的根源是**没有命名**——没有名字的东西不会被复用。
### D115（2026-11-11）**指标的"年"和"累计"必须回到被量的那个量去核对**：直觉语义会造出不可判定的阈值
**现象**：策略晋升闸读 `profitPerDay = income / 365`（`src/evolution/reflection-run.ts`）⇒ 两局 500 日真机得到的 "+£1662/年（4.55/游戏日）"被拿去向"每游戏日 > 16.67"的阈值下结论（"模型赚不到"）。复核 OpenTTD 15.3 源码后：admin 的 `income` 是**当前年迄今的净现金流**（不是运营利润）且**在年边界归零**（我们的局跑在 calendar 模式 ⇒ 经济年 = 日历年，边界 = 1 月 1 日）⇒ 500 日的局里这个数**只覆盖最后一年**；而除数 365 是**整年长度**，不是**这一局经过的天数** ⇒ **阈值与读数不同口径** ⇒ 那句结论**不可判定**（不是"模型赚不到"）。**同一族错误还有两处**：`gameDayFromRawDate` 用**虚构的 360 天年**（每年丢 5 天）⇒ "250 游戏日"其实是 ~256 日历天；`route-stats.ts` 的年内天数用 `gameDate % 365` ⇒ 不是年内第几天，且与分子（车辆 YTD 利润）的年**不同步**（事实见 `SPEC.md` §10.55 / §10.76）。
**根因**：写指标时用了**直觉语义**（一年 365 天、利润是累计的），没有去问"这个量被谁量的、它的**时间窗**是什么"；更糟的是**阈值和读数共用同一个直觉** ⇒ 两边一起错 ⇒ 错得"自洽"，任何一处都不会报错。第三层根因：**harness 自己有一本日历年**（360 天年投影）⇒ 凡是"每游戏日"的读数，分母都不是引擎的日历天 ⇒ **时间模型不对齐，速率类读数全不可信**。
**规则**：① 新指标/新阈值落地前先答三问：**谁量的**（引擎/admin/GS 的哪个字段）→ **时间窗**（年初至今 / 滚动 / 累计）→ **单位里的"年"是哪个年**；② 指标**名字必须能被读数直接兑现**：读数是"当年迄今"，名字里就不能出现"累计/整局"；③ **阈值与读数必须同一口径**，口径没核对前**不许用阈值下"做不到"的结论**；④ 代码里除以 365/360/90 的地方要能指出**依据**——没有依据的常数就是**虚构的年**；⑤ **一处时间模型**：日历换算只留一个实现，速率类读数的分母统一走它（`convertDateToYmd` 已是引擎口径的精确实现）。
### D113（2026-11-08）**入口判定必须比 realpath**：符号链接会让脚本**静默什么都不做**
**现象**：给 `scripts/bench.ts` 加了"import 时不许自动跑"的入口判定（`import.meta.url` vs `process.argv[1]`）⇒ 脚本**一行输出都没有**就退出了，退出码 0 ⇒ 矩阵"跑完了"，其实一格没跑。**根因**：macOS 的 `/tmp` 是 `/private/tmp` 的**符号链接** ⇒ `import.meta.url` 带的是**解析后**的路径，`process.argv[1]` 带的是**调用时**的路径 ⇒ 字符串比较判成"不是入口" ⇒ 顶层代码**永远不跑**。**规则**：① 入口判定比 **realpath**（两边都解析）；② "静默无操作"是最坏的失败形态 ⇒ 任何"脚本被调用"的路径都要有一条**会失败的回归测试**（`--dry-run` 打印矩阵 ⇒ 静默退出就会红）；③ 同样的判定在 `src/cli/run.ts` 里也有 ⇒ 一并修（仓库放在符号链接路径下会让 CLI 什么都不做）。
### D112（2026-11-08）**退出码只该回答一个问题**："harness 跑完了吗"，不是"结果好吗"
**现象**：每一局因为 token/花费上限、视界或墙钟而**正常收场**的运行，退出码都是 1 ⇒ CI 里全是红的 ⇒ **真失败被淹没**（没人看一个永远红的 CI）。**根因**：退出码被拿来表达"这一局的结果"（施工没做完 ⇒ 1）⇒ 而**结果**是 manifest 的 outcome 里的**事实**（结局十类，B5）⇒ 退出码与它重复且口径错位。**规则**：① 退出码只回答"harness 跑完了这一局吗"：正常收场（止损/暂停/施工没做完）⇒ **0**，真失败（GS 没起来、游戏崩了、抛错）⇒ **1**；② **结果**走 manifest，不走退出码；③ 判定"正常收场"时看**止损的原因**（预算/视界/墙钟），不看"结果好不好"。
### D111（2026-11-08）**一行的身份不等于它的实体 id**：一个产业可以按货种出现多次
**现象**：页面的"展开全部"点下去只画出 **6 行**（数组里有 48 行），而**控制台 0 错误**。**根因**：Alpine 的 `x-for` 用 `:key` 认行 ⇒ 我把 key 写成**产业 id** ⇒ 而产业列表是**逐 (货种, 产业)** 的（GS 的扫描就是按货种遍历的）⇒ 一个产两种货的产业**出现两次** ⇒ key 撞了 ⇒ Alpine 少画行。**规则**：① 列表行的 key 必须是**这行的身份**（(id, cargo)），不是它指向的**实体 id**；② 计数也要按**同一个口径**（"12 个产业"与"50 个产业"里若一个是行数、一个是实体数，就是两套口径 ⇒ 说明会自相矛盾）；③ 真实浏览器里数一数**画出来的行数**与**数组长度**（单测的假 DOM 不会重演 Alpine 的 key 冲突）。
### D109（2026-11-08）**Alpine 在微任务里启动** ⇒ 界面初始化要挂在 `alpine:init`，不是 DOMContentLoaded
**现象**：按 id 翻的服务端词汇（结局类、旋钮取值）在中文界面里**永远是英文**，而普通文案全对；手动把语言切一遍就好了（切换会重画）。**根因**：Alpine 的启动是 `queueMicrotask(() => Alpine.start())` ⇒ 它在脚本跑到一半时就开始**渲染** ⇒ 而 i18n 的初始化挂在 `DOMContentLoaded` 上 ⇒ **Alpine 先渲染，i18n 后初始化** ⇒ 渲染那一刻用的还是默认语言（英文）⇒ 那些按 id 查的词就停在英文（普通文案会被 i18n 事后翻好 ⇒ **只有这部分看起来"没翻"**）。**规则**：① 任何**渲染前必须就位**的全局状态（语言、主题、格式化器）都要挂在 `alpine:init`（Alpine 启动前触发）上；② 「一部分对一部分不对」通常不是随机故障，而是**初始化顺序**问题 —— 先问「谁先跑」。
### D110（2026-11-08）**服务端词汇按 id 翻，不要把它的措辞抄进前端表**
**现象**：结局十类、问题码这些服务端词汇在中文界面里是英文；按文案翻会把服务端的措辞抄进前端词表 ⇒ 那是**第二份**规范文案（B5 说服务端只有一份）⇒ 服务端改一个字，前端就悄悄回落到英文。**根因**：前端的词表按**源文本**作键，而服务端的措辞**不是前端的源文本** ⇒ 这类词天生不能进那张表。**规则**：① 服务端拥有的词按 **id** 翻（`outcome.token_cap`、`problem.no_credential`），没翻的 id **回落到服务端的原文**（不是空白、不是猜的翻译）；② 服务端要**把 id 一起发过来**（否则前端无从知道）；③ 守卫用**服务端的清单**校验词表的覆盖度（`OUTCOME_CLASSES` / `PROBLEM_CODES` / `PAIRED_METRICS`）⇒ 新增一个 id 而忘了翻，gate 直接红；④ 带变量的**分析结论句**（成长轴的斜率说明）保留原文 —— 翻它就要在前端复刻它的结构。
### D107（2026-11-08）**观察器挂在 `requestAnimationFrame` 上 ⇒ 页面不渲染时它就死了**
**现象**：中文界面里**动态渲染出来**的文字全是英文（静态文案正常），而控制台 0 错误、手动调一次 `translateTree()` 就全好了。**根因**：i18n 的 `MutationObserver` 回调把翻译挂在 `requestAnimationFrame` 上 ⇒ **rAF 只在页面正在渲染时才跑** ⇒ 无头浏览器里（页面不渲染）或标签页切到后台时，它**永远不触发** ⇒ `queued` 永远为 true ⇒ 观察器**从此死掉**，后面渲染出来的文字全是英文。**规则**：① 观察器的后续动作**不许依赖渲染**（用 `setTimeout(0)`，它还能把一串突变合并成一次翻译）；② 任何「页面一渲染就要跟上」的前端机制，都要问一句「**页面不渲染时它还成立吗**」；③ 这类故障**没有报错**，只能靠「在真实浏览器里量」发现（单测的假 DOM 没有观察器）。
### D108（2026-11-08）**「能不能翻」与「翻成什么」必须用同一个判断**
**现象**：复合摘要（`Money -£43,995 · Income -£43,995`）在中文界面里永远是英文：我给运行时加了「按分隔符拆开逐段翻」的能力，但**准入判断**（`isTranslatable`）不知道这件事 ⇒ 那些节点**从一开始就没被选中** ⇒ 新能力永远用不上。**规则**：判定与执行必须是**同一个函数**（`translateOnce` 同时回答「能不能翻」与「翻成什么」）；两处各写一套 ⇒ 一处改了另一处不知道 ⇒ 能力静默失效。
### D106（2026-11-08）**漏一条译文不会报错**：i18n 必须有"静态覆盖度"守卫
**现象**：中文界面**看着**有翻译，实际上四页 324 段静态文案里有 **226 段没翻**（半中半英），而**没有任何报错** —— 词表是「源文本作键」，漏一条只是"回落到源文本"。**根因**：gettext 模型的失败模式是**静默**的（页面不报错，只是那一句是英文）；而"翻了多少"这件事**没人查**。**规则**：① 守卫要按**运行时的同一口径**抽文案（否则守卫查的和运行时翻的不是一回事）；② 守卫查两件事：**每段可见文案都有译文** + **源文本里没有中文**（源里混进中文 ⇒ 英文界面出现半句中文）；③ 浏览器里还要查**往返**（中→英之后不留中文）。
### D105（2026-11-08）**还原要逐文本节点**：把原文写在父元素上会抹掉它的子元素
**现象**：i18n 运行时把原文记在**父元素**的 `data-i18n-src` 上，切语言时用 `textContent` 写回 ⇒ 父元素里的 `<code>`（`--agent`）、`<strong>` 被**一起抹掉**；而且"整段文本才翻"的规则让被内联 `<code>` 打断的句子**整句不翻**。**根因**：DOM 的还原单位是**节点**，不是元素；文本节点没有属性可挂，原文就得放在**它自己身上**（`WeakMap`）。**规则**：① 原文记在 `WeakMap`（键=文本节点）；② 还原前先确认"节点上还是不是我写的译文"——不是就**别动**（页面重新写过它）；③ 混合句要么整句不翻、要么**逐片段翻**（中文按片段写，读起来仍是一句）。
### D104（2026-11-08）**查表前必须归一空白**：DOM 的文本节点保留源码里的换行
**现象**：i18n 查表用 `text.trim()`，而 HTML 源码里换行写的句子在 DOM 里**仍然带着换行与缩进**（浏览器不会把元素内部的换行变成空格）⇒ 键对不上 ⇒ **那一句默默不翻**（实测：七句换行写的文案全部漏掉，且没有任何报错）。**根因**：查表键与 DOM 文本**不是同一个字符串**；源码的缩进是"看不见的差异"。**规则**：查表键一律 `text.replace(/\s+/g, " ").trim()`；**凡是"用字符串当键"的机制**（缓存键、去重键、匹配键）都要问一句"我拿到的是不是同一个形态"。
### D97（2026-11-08）**聚合数推不出配对 CI**：配对统计的原料是**逐对**的差值
**现象**：ROADMAP 待办写着"用旧 6 格补次级轴的配对 CI（0 token）"；2026-11-08 复查磁盘：`/tmp/pB1..pB6` **只剩空目录**，全盘找不到 `metrics.jsonl` ⇒ 旧格子的**逐行读数**没了，只剩聚合数（每 1M token 交付 1635 vs 1033、工具失败率 13.1% vs 2.9%）。**根因**：把**统计结论**当成了**统计的原料** —— 配对 CI 需要每对 (seed, repeat) 的**两个值**（差值由此算出），而均值/比率**不可逆** ⇒ 聚合数推不出配对 CI。**规则**：① 要留的结论必须同时留**它的原料**（基准的度量行是资产，不是临时文件；跑完矩阵别删 data dir）；② 说"用旧数据补统计"之前，先确认**原料还在**；③ 更好的答案是**让统计能力泛化**（配对统计支持任意轴），而不是抢救旧数据。
### D103（2026-11-08）**容器形状装不下事实 ⇒ 两种事实就分成两种容器**，别“字段留空兼容”
**现象**：真机货运局留下的 `route-facts.jsonl` 里 5 条货运线是 `from:null,to:null` ⇒ 注入模型的句子成了 `route towns null->null was ordered at decision 2` ⇒ **垃圾进上下文**（不只是脏数据，是给模型的噪声）。**根因**：台账只有一套形状（“两端城镇”），而货运线的两端是**产业** ⇒ 硬塞 ⇒ 两端都 null。**规则**：① 容器的字段要么**覆盖全部种类**，要么**显式分成两种记录**（本仓选了后者：`kind: passenger|freight`，幂等键里也带**种类与两端** ⇒ 两种线不会互相覆盖）；② “字段留空兼容”不是兼容，是**把事实降级成 null**；③ 修完要在**真机**上读落盘的事实行，确认没有 null 端点。
### D102（2026-11-08）**“事实表里有”≠“它发出去了”**：状态包是**逐字段拷贝**的
**现象**：给 GS 的事实表加了 `own_by_industry`（逐 (货种, 产业) 的读数）⇒ 事实表里确实有 ⇒ 但真机跑了 420 秒、**交付 160 吨煤**，而 harness 收到的状态包里**没有**这个字段（`own_delivered` 有、`own_by_industry` 没有）⇒ 归因的原料是空的 ⇒ **无报错、无告警**。**根因**：GS 的状态包是**从事实表逐字段拷贝**的（`own_delivered = (f == null) ? ### D101（2026-11-08）**判定词说的是方向，不是胜负**：效率轴上“更大”通常是“更差”
**现象**：逐轴配对表上线后，墙钟那一行写着 `b_higher` ⇒ 读者会以为 “b 更好”，而**墙钟越短越好** ⇒ 页面把方向读反了。**根因**：判定词 `a_higher` / `b_higher` 只回答“谁的数字更大”，**不回答“谁更好”**；而每个指标的**好坏方向不同**（交付越多越好 / token 越少越好 / 站点数无好坏）。**规则**：① **方向 ≠ 胜负** —— 凡是带质量判断的展示，**好坏方向必须由服务端按指标给出**（指标目录里一个字段），页面不许自己推断；② **没有好坏方向的指标就明说**（“no quality”），不要为了填格子硬给一个赢家；③ 展示“更好”时**同时给出方向**（`stub-b (lower is better)`），否则读者仍会误读。
### D99（2026-11-08）**配对要按“局”定，不能按“有读数的行”定**：否则一个缺读数就会把两局错配
**现象**：把配对统计从主轴泛化到任意轴（Issue #87）后，发现旧实现的槽位编号是在**过滤掉“没测到”的行之后**才算的（`cellMap` 先 `value === null` 就 `continue`，再数 `seed#i`）⇒ 同一个 (seed, repeat) 在不同轴上**指的不是同一对局**：A 的第 1 局在主轴上有读数、在稳定性轴上没读数（`toolCalls = 0`）⇒ 稳定性轴上 A 的第 1 局被挤到槽 1 ⇒ 与 **B 的第 1 局**配成一对 ⇒ 差值算成了“错的局 vs 对的局”。**根因**：把“槽位”当成了“这一轴上有读数的行序号”，而槽位本该是**局的身份**。**规则**：① 配对的键（seed + 重复序号）必须**与指标无关** —— 先把所有**可比较**的行定成局，再逐轴取读数；② 一个轴缺读数 ⇒ **整格丢掉**（n 变少），**不许**让后面的局往前挪；③ 写完配对逻辑后，手工验一遍“两局的对应关系”在各轴上**一致**（单测锁住：某轴缺读数 ⇒ n 减 1 且差值不变）。
### D100（2026-11-08）**验收探针自己也会坏**：“点了按钮” ≠ “按钮生效”
**现象**：用 CDP 探针验收 Compare 页的逐轴表：点两个复选框、点 “Compare the two”，读回来的表格 **tbody 是空的**、`visible: false`，而 console **0 条错误**。**根因**：按钮上有 `:disabled="picked.length !== 2"` ⇒ Alpine 更新 `picked` 后要**下一轮渲染**才把 `disabled` 去掉 ⇒ 探针在**同一个同步块**里立刻 `click()` ⇒ 浏览器对 disabled 按钮**不派发 click** ⇒ 页面根本没请求过带 `models` 的接口 ⇒ 空表 + 无报错。**规则**：① 探针要**等条件成立**（轮询到 `disabled === false` 再点），不能假设“点了就生效”；② “表格是空的 + console 干净” ⇒ **先怀疑自己的探针**，再去查页面（用一个**手写 fetch** 同参数对照，能立刻分辨是服务端没数据还是页面没渲染）；③ 页面**没报错**不等于**没坏**（D45 同源）。
### D98（2026-11-08）**事实容器的形状必须装得下它要记的事实**：装不下就会写垃圾
**现象**：真实模型货运局留下的 `route-facts.jsonl` 里，**5 条货运线**是 `from:null,to:null` ⇒ 注入模型的句子成了 `route towns null->null was ordered at decision 2`。**根因**：路线台账的记录形状是"两端**城镇**"（`from`/`to` 是城镇 id），而货运线的两端是**产业** ⇒ 硬塞 ⇒ 两个字段都变 null ⇒ 事实退化成"null 对 null"，而它**还在进模型的上下文**。**规则**：① 容器的字段要么**覆盖全部种类**（客运城镇对 / 货运产业对 + 货种），要么**显式分成两种记录** ⇒ 不能靠"字段留空"兼容；② 装不下时**拒收**并说清原因，不要写半条事实；③ 记下来的东西会**进上下文** ⇒ 垃圾不只是脏数据，是**给模型的噪声**。
### D96（2026-11-08）**"车站收不收货" ≠ "产业交不交货"**：两个闸别混
**现象**：货运 F1/F2 的整个设计建立在一个推断上："矿场旁的车站**不收煤** ⇒ 煤装不上车 ⇒ 这条货运线不成立"（探针实测车站收货 0 ⇒ 我们据此判了"运不走"）。**根因**：那是**两个不同的机制** —— **交货**看车站的 **rating**（`CanMoveGoodsToStation`：`rating == 0` 才拒收；新车站的 rating 是 **175**）⇒ **车站不收这个货，产业照样把货送到站上等着**；**卸货**才看**收货**（`LoadCargo`/`UnloadCargo`：站不收货 ⇒ 货被退回而不是交付）⇒ 装货侧只要罩住产方，卸货侧必须收货 >= 8。**规则**：① 引擎的"收货（acceptance）"与"评级（rating）"是两套闸，**别用一个推另一个**；② 探针测到 0 先问"这是哪个闸的 0"；③ 集货半径是 **3**（15.3 默认开着 modified_catchment；`CA_UNMODIFIED` 才是 4）⇒ "一座车站同时罩住产方与收方"在多数图上**不成立**（seed 4242 最近的一对是 15 格）。
### D94（2026-11-05）**空结果 ≠ API 不存在**：先查"我们的代码自己有没有抛异常"
**现象**：2026-11-01 判定"OpenTTD 15.3 的 Squirrel 没有 cargo monitor，拆分不可测"，写进了 SPEC/MEMORY/守卫；2026-11-05 复查源码（`script_cargomonitor.hpp` 写着 `@api game` ⇒ Squirrel 侧也导出）＋真机探针 ⇒ **API 一直在**，调用成功、返回 0。**根因**：我们的累加器写了 `table[label] = …`，而 **Squirrel 的表是严格的**（往不存在的键写会抛 `the index 'LVST' does not exist`）⇒ `CollectFacts` 整个抛异常 ⇒ 事实表永远没更新 ⇒ "拆分永远是空的" ⇒ 被误读成"API 返回 null"。**规则**：① 看到"永远是空"，**先查我们自己的异常**（GS 的 `gsErrors` / 脚本报错），再判引擎的罪；② 探针的**异常通道**要对：第一次探针的 `catch` 块又写了同一个不存在的键 ⇒ 连 catch 都救不回来（D44 的老坑）；③ **"0" / "空" / "null" 是三件事**；④ 怀疑 API 不存在时，源码的 `@api` 标签 + 一次真机调用**两样都要做**（调研见 `docs/PER-LINE-DELIVERY-FEASIBILITY.md`）。
### D89（2026-11-01）"调用没报错"≠"调用有效"：脚本 API **不存在**时它返回 null
**现象**：给分数轴加「货物 vs 客运」拆分，GS 里调 `GSCargoMonitor.GetTownDeliveryAmount(...)`，跑完 333 游戏日、交付 894 单位，**拆分一直是空的**。**根因（2026-11-05 纠正）**：**不是**脚本 API 没有 cargo monitor（它有，见 D94）—— 是**我们自己的累加器抛了异常**（Squirrel 的严格表）。本条要保留的教训是：**"没报错"不等于"有有效读数"，也不等于"API 不存在"**。**规则**：① 用任何 API 前先查它**存在**（`squirrel-api-guard` 的 `KNOWN_BAD_CALLS` 登记**已知不存在**的 API —— 但那份名单本身也会过期，见 D94）；② **静默返回 null/0 的 API 必须用"真机有非零读数"验证**；③ 自己**声称已实现**的效果，必须有一条真机证据说明它真的有数。

### D88（2026-10-31）账本的键必须**每局唯一**；丢了行必须**报出来**
**现象**：第一轮基准矩阵 6 格里 Compare 页只显示 "1 model(s)"，而 6 局都跑完了 ⇒ 账本少了 3 行且**无任何提示**。**根因**：session id 是 `<秒级时间戳>-seed<n>` ⇒ **同一秒 + 同 seed 的两局撞号**（两个模型并行必撞）⇒ 账本"同 id 取最新" ⇒ 另一行静默消失。**规则**：① 任何"按 id 去重"的存储，键必须**每局唯一**（精度不够就加随机后缀）；② **丢行必须报出来**（账本返回碰撞数，页面写明"这些局不在下面的任何数字里"）——样本悄悄变少是基准最容易骗人的方式。
### D87（2026-10-31）"完成"不等于"跑完"：墙钟闸默认 180 秒，长跑必须显式给

### D86（2026-10-30）"数据到了管道里"不等于"模型看得见"：投影是最后一道闸

**现象**：GS 早就在报产业、货种总量、车型目录和镇名，hub 早就在解析——**而模型只看得到 `date` + 公司 + `towns[{id,pop,x,y}]`**。真实模型自己发现了（"observe 输出没有 cargo 标签和车型表（看起来被截断了）"），随后建了客运线，分数（货物吨数）恒为 0。 **根因**：管道（GS → hub → 世界状态）与**模型可见的投影**（`worldFacts()`）之间有一道闸，而没有任何测试覆盖它——单测测的是"投影里有没有这个字段"，不是"模型看得见这个字段"。

### D117 —— 持久化路径不能直接 `JSON.stringify`：BigInt + 空 catch = 静默的数据丢失（2026-11-11）

**现象**：修 Issue #104 的收益读数时发现，**归档里一条 `company_economy` 都没有** —— 而 harness
明明收到过（世界状态里有 `income`、`deliveredRun`）。`src/agent/session-store.ts` 的 `appendJsonl`

没有报错、没有计数、没有日志。后果不只是“少一个字段”：归档是**离线重算的唯一原料**，丢了一类事件
⇒ 跑过的局**永远**无法按新口径重算（B2 两局因此不可重算）。

**根因**：① 仓库里早就有 BigInt-safe 的序列化器（`src/util/json.ts`，文件头写着“**禁止**在事件/日志
路径上直接 `JSON.stringify`”），但**归档路径没用它** —— 规则写在工具里，没人在调用点被强制；
② “持久化失败不能中断这一局”这条正确的工程要求，被实现成了**空 catch** ⇒ 把**类型错误**也变成了
“什么都没发生”。要求本身没错，错在**失败不可见**。

**规则**：① 事件/日志路径**只有一个序列化器**（`stringifyJson`），调用点不许自己 `JSON.stringify`；
② 吞异常的 `catch` 必须**留痕**（计数器或日志行）——“不打断这一局”≠“失败不可见”；③ 归档是离线重算的
原料，**丢一类事件等于毁掉所有旧局** ⇒ 写归档的路径要有“这一类事件写了多少条”的读数；
④ 归档里“找不到某个读数”时，**先查写的人，再查读的人**（本例读的一直是对的）。
**修后的真机对照**：同一份跑法，旧归档 `company_economy` **0 条**，新归档 **792 条**（同一局）⇒
这条不是“推测”，是数出来的。

### D118 —— 归零型计数器不能直接当“本局累计”：去找跨边界连续的底座（2026-11-11）

**现象**：`income` 是**当年迄今净现金流**，1 月 1 日归零 ⇒ 跨年的局拿它当“这一局的收益”必然只覆盖
最后一年（D115）。直觉的修法是“把跨年的段积分起来”，但那要先解决“每段读数归属哪一年”的歧义
（边界那条读数带的还是**上一年的完整值**）。

**根因**：没区分**读数的类型**。`income` 是**流量型年初至今计数器**（有归零日），而“这一局的收益”是
**区间量** ⇒ 正确的底座是**跨边界连续**的存量：`money − loan`。查引擎源码得到两条关键事实：
每笔费用都做 `money -= cost` 与 `yearly_expenses += cost`（同一笔，费用类型不同而已），借款让
`money` 与 `current_loan` **同增同减**，贷款利息**按月**计（不在年边界）⇒ **`Δ(money − loan)` 就是
任意窗口的净现金流，跨 1 月 1 日成立**；再查**初始化**那一行：创建公司时 `money = current_loan`
⇒ `money − loan` 自创建起就是 0 ⇒ 最后一条读数的 `money − loan` 直接就是“本局自创建以来的净现金流”，
不需要年初基线。

**规则**：① 新读数先**分型**：存量（余额）/ 流量（每单位时间）/ 年初至今计数器 —— 只有最后一类有归零日；
② 要“本局累计”时，找**底座**（现金/贷款/存量），用差分，别用会归零的计数器；③ 引擎事实要查到
**初始化**那一行（它决定底座的起点）；④ 分段与**对账**另做（用引擎自报的整年值核对每一段）⇒ 对不上
就是**缺口**，必须报差值而不是折零（D60）。

### D120 —— "逐桶比较"会把**采样相位**误判成**世界分叉**（2026-11-12）

**现象**（做 #106 的确定性探针时）：判据写成"逐日比较资金轨迹"⇒ 两次读档在 **day 17 差 £4921**
⇒ 结论"同存档不可复现"⇒ **差点把一个测量缺陷当成引擎的结论**（并据此否掉 P5 反事实 fork）。

**根因**：**钱是事件驱动的**（只在施工那一刻变），而读数按**墙钟**轮询，且 admin 的**日期包与经济包各自到达**
⇒ 一笔支出落在"这一天"还是"那一天"取决于**采样相位** ⇒ 同一局读两次，**同一天的钱就可以不同**。
换成**与相位无关的量**（钱**经过的取值序列**，即"档位"）后：两局**档位集合与顺序完全相同** ⇒ 引擎侧其实**可复现**
（`SPEC.md` §10.113）。另有一条独立事实：**脚本自身的状态不随存档存取**（GS 与 ExecutorV1 都没有 `Save()`/`Load()`
⇒ 引擎记 "Save function is not implemented"）⇒ 读档后 GS 从零重启 ⇒ 读档那一轮**不是**原那一轮的续跑。

**规则**：① 拿一个量做"两局是否一致"的判据前，先问它是**事件驱动**还是**采样驱动**——事件驱动的量
**按取值集合/顺序**比，**别按时间桶**比；② 看到"分叉"先问"这是**相位**还是**分叉**"（换一个与相位无关的量再看一遍）；
③ "引擎不可复现"这种结论**必须能区分相位与分叉**才写进 SPEC；④ 判据本身要有单测，且**能说"没测到"**——
两局都没读到钱时"集合相同"是空洞的真（`src/util/money-levels.ts` 的 `measured` 字段）；⑤ 还要能说"**没有鉴别力**"——
两局的钱**从头到尾没变**（只有一档）⇒ 任何两局都"相同"⇒ 这**不能**证明"可复现"（`powerful` 字段）⇒
探针的窗口太短时**必须报"没测到"**，而不是报一个空洞的"相同"。

### D119 —— "探针连上了"不等于"探针在听"：握手、订阅、GS 三件事各自会静默（2026-11-11）

**现象**（做 #105 的真机探针时）：自写的探针用 `AdminClient.connect()` 连上 admin 端口 ⇒ **连接成功**，
但 GS 的状态推送一条都收不到，`gameScriptAwait` 全部超时 ⇒ 第一反应是"GS 没起来 / 我的新命令炸了"。
真相有三层，每层都会静默：

1. `connect()` 只完成 TCP 连接；**握手要等 `Welcome`** ⇒ 半开连接看起来是"连上了"但收不到任何东西
   （harness 用的是 `connectAuthed()`，它会等 Welcome 并重试）。
2. GS 的推送（`GSAdmin.Send` → `NetworkAdminGameScript`）**只发给订阅了 gamescript 的 admin 客户端**
   ⇒ 没订阅就一个字都收不到。
3. GS 的命令是**事件驱动**的（`GSEventAdminPort` ⇒ `Dispatch(obj)`）⇒ 命令没进 GS 就不会有回答，
   "超时"不等于"命令被拒绝"。

**根因**：探针自己复刻了一份"连上去就行"的假设 ⇒ 把**三层静默**看成一层 ⇒ 差点把"GS 的新代码有问题"
当成结论（真去改了 GS 才发现 GS 没问题）。

**规则**：① 探针**复用 harness 自己的客户端与订阅**，别写裸 socket；② "GS 没回答"先查**握手完成**
（`isAuthed`）与**订阅**，再怀疑 GS；③ 探针的第一次"没反应"要能区分**没发出去 / 没被订阅 / 被拒绝**
三种；④ 顺带记一笔：有一次探针的首次连接让专用服务器在 admin 的 accept 路径里 abort（fmt 异常，
**一次观测、未能复现**）⇒ 若再出现，这是引擎侧的问题，不要改 harness 绕开。

### D121 —— "线建成了"不等于"线在跑"（2026-11-12，Issue #113）

**现象**：真机（seed 4242，COAL 46→53）里货运线**建成了**（`stA_ok`/`stB_ok`/`road_built`/
`dpt_conn`/`trk_live`，车队 2 辆）、车**装对了货**（admin 口径 `truck: 2` ⇒ 引擎按货物类别分类 ⇒
改装生效；`GetCapacity(v, COAL)` = 20）、车**带着两条车站订单**、车**到了装货站并开始装货**
（引擎的 `station_first_vehicle` 事件），但**装走 0 吨**，整局**交付 0**，装货站的煤从 0 涨到 290（复现局）/303（原局）。

**根因（两层）**：① 周期读数只报"几辆车在等多少"⇒ **看不见车卡在哪** ⇒ 模型与人只能猜；②
**装不上货的引擎侧条件仍未定位** ⇒ 已排除的猜测：**不是"货没有下一跳"**（引擎按下一跳装货，
但 `GetCargoWaitingVia(装货站, -1, COAL)` = 290 ⇒ 货包在"无下一跳"那一桶 ⇒ 兜底允许任何车装它）
⇒ ⇒ ⇒ **⇒ 猜测必须被测量否掉，不能被推理否掉** ⇒ 诊断工具的存在意义就在这里。

**规则**：
① **动作完成 ≠ 结果发生**："建成"与"在跑"必须**分别**可查 ⇒ 任何"完成了"的报告都要能被**问出来**。
② 诊断走**按需**通道（周期载荷不许变大，SPEC §10.126）；GS 只报**事实**（车在哪、订单是什么、
装不装得了、两端在等多少），**具名原因由服务端算**（封闭词表 + 单测，`src/agent/route-diagnosis.ts`）。
③ **"没测到"与"没问题"分开**：诊断读不到就写 `not measured`，不许折成 0 或"没问题"。
④ **同一 seed ⇒ 现象逐字可复现**（实测两次探针的车站瓦片与相位序列完全相同）⇒ 能定位 ⇒ 先复现再猜。
⑤ **量之前先问这个量是什么**：车站占**两块地**（标牌格 + 路旁格）；**`AreRoadTilesConnected`
只答"相邻两格连不连"**（引擎第一句就是 `DistanceManhattan != 1 ⇒ false`）⇒ 拿它问"两站通不通"
永远得到 false ⇒ **假读数比没有读数更坏**；执行器的**完工记录会覆盖施工期的记录** ⇒ 诊断要读**同一个**记录。
⑥ **Squirrel 的表键规则**：空表 `null.rawin(...)` 直接炸；**动态键（车 id）用 `t[k] = v` 也会炸**
（"the index 'k' does not exist"）⇒ 只能用 `rawset` ⇒ 诊断命令整条失败时，模型看到的是"没有路线"
而不是"诊断不了" ⇒ 新表**先初始化**，动态键**只写 rawset**。

### D122 —— **声明的参数 ≠ 兑现的参数**（2026-11-13）

**现象**：`get_industries(cargo)` 的 schema 写着"传货种标签就只给这个货种的产业"，工具也确实把
`cargo` 发给了游戏（`{"cmd":"list_industries","cargo":"COAL"}`），**但 GS 的 `list_industries`
根本没读这个参数** ⇒ 模型问"只要煤的产业"、拿到的是**全图** ⇒ 工具的**摘要**还写着"N 个产业
（全量）" ⇒ **模型、工具、看板三处都在说一个没有发生过的过滤**。

**根因**：参数的**传递链**没有端到端的**守卫**——只测了"参数发出去了"，没测"**收的人真的按它过滤**"。
静态测试只钉住"命令被接线"，不钉住"参数被使用"⇒ 两者之间有一个**没人看的接缝**。

**规则**：
① **工具的承诺必须能在世界里兑现**：每个**声明了语义**的参数，都要有一条**端到端**的断言
（发出去了 **且** 收的人按它过滤了 **且** 结果与承诺一致）。
② **"没测到"≠"没有"**：过滤结果为空时，要区分"**这个标签不存在**"与"**这个标签下没有产业**"
⇒ 前者回**可用的标签**让模型自己改，后者才是 0（缺失 ≠ 0，D60）。
③ **GS 只报事实**：过滤是**读侧查询**，归 GS（它知道这个世界有哪些标签）；**摘要由服务端按
回答写**，不许出现"全量/过滤"与实际给出去的不一致。
④ 改工具的**描述**就是**换脚手架**（指纹覆盖工具表）⇒ 这次改动让脚手架指纹从
`d51169a91e2464e1` 变成 `971f2be679712715`，此后所有局与之前的局**互不可比**。

### D123 —— **引擎给的"当年迄今"不能当"这一局的累计"**（2026-11-13）

**现象**：要给"公司级运营利润"（运货收入 − 运行成本）一个**本局连续**的读数时，最省事的做法是
直接读引擎的 `GSVehicle.GetProfitThisYear` ⇒ 但它是**当年迄今**：① 1 月 1 日被引擎清零 ⇒
跨年的局读数**凭空掉一截**（看着像亏损）；② **车被卖掉时它带着自己的历史一起消失** ⇒
"公司的累计"少了一块；③ 从存档起步的局里，车**带着上一段历史**的利润 ⇒ 直接拿来当"本局的利润"
是**把别人的账算进这一局**。

**根因**：**读数的口径**（当年迄今）与**要回答的问题**（这一局赚了多少）是两个东西；引擎只给前者。
凡是要"累计"，就必须有一本**自己记账的账**。

**规则**：
① **累计量由服务端记账**：第一条读数**只建基线**（不算本局），之后只加**增量**；
后来才出现（新建）的车，它的读数**全额计入**（它存在期间攒下的就是本局的）。
② **卖车不得清零**：车从车队里消失 = 被卖掉 ⇒ 它本局的累计**冻结并留在账上**。
③ **读数下降不是亏损**：跨年时引擎把当年利润清零 ⇒ 年界只**挪参照点**，不清空本局累计
（否则会把"跨了一年"读成"亏了一年"）。
④ **不完整就说"是下界"**：中途卖车或跨年没采到 ⇒ `complete=false` ⇒ 这个数是**下界**，
不能装作精确（缺失 ≠ 0，D60 的同型）。
⑤ **三个量不可互换**：**运营利润**（运货收入 − 运行成本）≠ **净现金流**（`money − loan`，
含基建/购车/利息）≠ admin 的 `income`（当年迄今净现金流）。晋升闸问"这条线赚不赚钱"⇒
那是运营利润；"这一局花了多少"⇒ 那是净现金流。混称会把基建支出算到线路头上。

### D124 —— **机制能用 ≠ 这一局看得见它**（2026-11-14，Issue #113）

**现象**：Issue #113 说"货运线建成了却不交付：整局交付 0"，看起来像**机制坏了**。
2026-11-14 的真机跑出了相反的结论：这条线**能交付** —— 车在装货站**停进站、装满 20 吨**
（装货站等待量同步下降），开到卸货站**卸货**，cargo monitor 报出
`own_by_industry = [{COAL, 53, 10}]` ⇒ **交付真的发生了**。

**根因**：**不是机制坏了，是这一局不够长**。① 引擎按**订单表**跑（`[A,B]` 循环）⇒
**第一次**到装货站时站上**还没有煤**（矿场要慢慢产）⇒ 空车先跑一趟卸货站；
② 单程 177 格 ⇒ **一轮往返要上百个游戏日** ⇒ 400 日的局常常只够**装上**、来不及**送到**
⇒ 看板上的"交付 0"其实是"还没送到"。

**规则**：
① **报"没有交付"之前先量周期时间**：一趟要几个游戏日？局的视界是几个？两者一比，
"坏了"与"太慢"就分开了（分不开时**说分不开**，别挑一个信）。
② **"机制能用"与"这一局看得见它"是两件事**：一个 900 日的局能看见，一条 300 日的局看不见。
③ **诊断要读到引擎的判据**，不是读现象：卸货端**收不收**（收货额度 >= 8 才收，否则引擎把货
**留在车上**）、装货端**评分是不是 0**（0 = 产业不再交货）、站牌格**有没有相邻的路**、
引擎自己的**入口格**（车从这边开过来才会停）—— 这四个是引擎事实，具名原因由服务端算。
④ **"引擎按订单表跑"不是 bug**：它不会在站上等货 ⇒ 想要"等满再走"得由脚手架**显式要求**
（订单的 load 类型），不能指望引擎。

### D125 —— **两个口径并存时，别按下标对齐**（2026-11-14，策略晋升闸换度量）

**现象**：把策略库的晋升闸从"净现金流"换成"运营利润"（方案 C：两个口径并存）后，
**两局累积读不出来**：卡上只有一个读数，第二局的读数没进数组。看起来像"闸的逻辑错了"。

② **变量遮蔽函数**：局部 `const operatingReadings = new Map(...)` 与同名的

④ 这类"静默少算"只有**端到端的测试**抓得到：单元测试造卡是对的，坏的是**合并路径**
（`readStrategies` → `mergeStrategySamples` → 落盘 → 再读）。

### D126 —— **admin 的 `delivered` 是当季计数，不是整局累计**（2026-11-14，E1 预登记）

**现象**：E1（工具预算 A/B）的预登记把主读数写成 `delivered`（admin 口径）。跑完 4 格后，
判定**冲突**：按 `delivered` 是 RULE 2（预算不是约束），按 `deliveredRun` 是 RULE 1（是约束）。

**根因**：`delivered` 来自 admin 的 `deliveredCargo`，**那是当季计数**（季边界 = 1/4/7/10 月 1 日，
`SPEC.md` §10.55 早就写着）⇒ 两局**结束时刻所在的季度不同**时，它量的根本不是同一件事
（实测：一局 `delivered=518` 另一局 `delivered=0`，而两局的 `deliveredRun` 都是正的）。
整局累计是 **`deliveredRun`**（跨季度积分，harness 的 `deliveryMeter`），**分数卡的能力轴一直用它**。

**规则**：
① **跨局比较用整局累计**（`deliveredRun`）或它的**每游戏日**速率；季度计数只能用于"本季怎样"。
② 写预登记时，若某个读数**可能有两种口径**，**先查清它是哪个再写**（查 SPEC §10.55 / 读它的实现）。
③ 结论类问题（"闸可达吗"）必须用**闸真正读的那个量**回答。
④ 预登记的读数写错时，**改读数不改判据**，并把改的理由与两个口径的结果**都报出来**——
否则就是"事后挑数据"。本次：判据形式（RULE 1/2/3）未变，只把主读数换成项目自己的能力轴所用的量。

### D127 —— **「谁拥有这些车」只有一个真值：执行器注册表**（2026-11-15）

**现象**：逐线的车辆数与利润是**错的**，而且**不报错**：
- job 1：注册表 10 辆车 ⇒ 报 `vehicles=20`、`profit=14152`（真值 7076，**正好 2 倍**）；
- job 9：**注册表 0 辆车**（它根本没建成）⇒ 却报 `vehicles=10`、`profit=7076`——
  **那是别人线路的车与利润**。
两个数都进**模型上下文**（模型据此判断哪条线赚钱）⇒ 模型在按假事实决策。

**根因**：`GSVehicleList_Station(s)` 返回的是**服务该站的车**，不是"此刻停在那儿的车"。
① 一条线的车在**两个端点站**各出现一次 ⇒ 扫两端 = 同一批车数两遍；
② 站被**共用**时，别条线的车也在列表里 ⇒ 串线。
旧代码把它当"站点归属"，并在页面层靠 id 去重（`SPEC.md` §10.105）——**去重的是症状，根在源头**。

**规则**：
① **归属类读数（谁拥有哪些车）只有一个真值**：执行器注册表（`RouteVehicles(job)`）。
   站点/位置是**观测**，不是**归属**。
② **进模型上下文的数字必须先验归属**：一个数字错了，模型就会按它决策（这不是显示问题）。
③ 静默的测量缺陷要配**静态守卫**（`test/unit/route-stats-attribution.test.ts` 直接扫 GS 源码）：
   单元测试跑不到 Squirrel ⇒ 没有守卫它会**再犯**（它已经静默存在了几个月）。

### D128 —— **总量不是能力的标量**（2026-11-15，基准矩阵的『真根』）

**现象**：矩阵结论『能力轴 `not determinable`』。总交付量的方差由**『建没建线/建了几条』**主导
（M2.5 有一局什么都没建 ⇒ 0 交付；别的局建了 7 条线 ⇒ 446 交付）⇒ 配对 CI 跨 0。

**根因**：**总量 = 数量 × 单位产出**。数量是**建造策略**的选择（不是模型能力），
而矩阵拿它当能力标量比。

**规则**：
① 比较『能力』要**归一化**：每条线/每辆车的交付与运营利润（`src/evolution/normalized.ts`）。
② 归一化的**分子用公司级读数**（整局累计交付、运营利润——干净），**分母用干净的计数**；
   不用逐线读数当分子（逐线利润是『当年迄今』，且历史上归属还算错过，D127）。
③ **分母为 0 的局（一条线都没建）在归一化轴上不可比** ⇒ 不参与配对，
   **不是**『每线产出 0』（后者会把『模型没动手』说成『它建的线没用』）。
④ 归一化是**度量选择**（脚手架的活），不是模型的事 ⇒ 改它要写进 SPEC 并锁测试。

### D129 —— **重建一张表 ⇒ 静默丢掉其余字段**（2026-11-16）

**现象**：执行器每次车队变更/退役/改货/换车都用 `this._routes[job] <- { … }` **重建**线路记录、
只写回自己关心的几个键 ⇒ 表里**其它字段被丢掉**。丢掉的包括 `lineCargo`（线路运的货）⇒
**货运线没有 cargo 标签** ⇒ 逐 (货种, 收方产业) 的归因**永远归不出来** ⇒ F4 的**逐线交付量在真机上
从未出过一个数**（E1 局：11 条线里 6 条货运线的 `cargoCarried` 缺席）；还有 `endA/endB`（诊断用的两端格）。

**根因**：把「更新记录」写成了「重建记录」。Squirrel 的 `<-` 是**替换整个值**，不是合并。

**规则**：
① **就地改字段**（`r.vehicles = …`）；只有「登记一条新记录」才重建整张表。
② **「新建」与「更新」是两种操作**，别用同一种写法；新建要写全字段。
③ 任何重建都要问「**这张表还有谁在读？**」——丢的字段常常**进模型上下文**（模型据此决策）。
④ 静默丢失要配**静态守卫**：GS 源码里那张表的重建写法**只允许出现一次**（本例：`RegisterRoute`）。

### D130 —— **「上一次决策的耗时」是一个样本，不是分布**（2026-11-16，E2 矩阵）

**现象**：E2 矩阵的 prebuilt 格里，seed 11/33 各只有 **1 次决策**（28 次工具调用全在这一次里），
整局变成「1 次决策 + 空转到视界结束」。这正是 AGENTS §5.1 点名的失败形态（`decisions=1`
⇒「只问了一次」）⇒ **矩阵测的是脚手架，不是模型**。

**根因**：决策余量（"离视界太近就别再问了"）取的是「**上一次决策吃掉的游戏日**」，而
**世界在模型思考时照跑** ⇒ prebuilt 里模型第一次决策（28 次工具调用 ≈ 140 秒墙钟）吃掉
**90+ 个游戏日** ⇒ 余量(≈183 日) ≥ 视界剩余(182 日) ⇒ 循环**再也不提问**。
一次慢决策就关掉了整局的提问——因为「上一次」是**一个样本**，不是分布。

**规则**：
① **凡是「估计量」都要封顶**（余量封顶 30 日 = 一个月的决策节拍）：一次慢决策最多
   推迟提问，不能取消剩下的视界。
② **基准跑完先查 `decisions ≥ 2`**（AGENTS §5.1 的硬要求）——那是「模型真的被反复问过」的
   最小证据；**先怀疑脚手架，再读结果**。
③ 测量缺陷要**当场对照 AGENTS 的硬要求**，而不是等结论出来才发现整轮作废。
