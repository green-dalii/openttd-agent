### D52. agent 用工具结束了自己的 episode，而仪表盘看不出是谁停的（2026-09-23）

**现象**：项目所有者问："我也已经点击 Pause 了，怎么还在跑？难道控制机制没接线？"

**取证**（不是猜）：
- `/api/run` → `state: "paused"` ✓ 控制**是**通的；
- 页面截图 → `RUN: paused · agent`、按钮已变 `Resume`、`LAST DECISION: 5 hours ago`、游戏日期与
  事件数 10 秒内**完全冻结** ✓ 世界确实停了；
- 但审计里最后一条动作是 **`set_pause — rcon pause answered: ""`**，而**最后一次决策就是 turn 90**，
  即 **agent 自己把游戏暂停了**，此后 5 小时循环再没跑过一次。 所有者按 Pause 时状态**早已是** paused，于是"为什么还在跑/为什么停了"根本无从判断。

**三个根因（都是"陈述与世界不一致"）**：
1. **回执措辞**：`rcon pause answered: ""` —— 空回复其实是**正常**的（OpenTTD 的 `pause` 控制台
   没有输出，`SERVER_RCON_END` 到达但零行），但这句话**既读不出来**，又把"投递成功"说成了 "命令生效"。投递与效果是两件事：效果只能由世界证明（暂停时游戏日期停止前进）。
2. **归因缺失**：`pausedBy` 不存在。页面按钮与 agent 工具**都**能暂停游戏，但状态里只有
   `paused`。**"谁让它停的"是一个独立事实**，必须记录（且**第一个让它停的人才是原因**， 后到的暂停不得覆盖）。
3. **没有"数据已陈旧"的信号**：暂停后页面照旧渲染（telemetry/心跳仍在），看起来还活着。

**规则**：
- 一个能让世界**停止前进**的工具（暂停/冻结/停表），其效果必须能被**独立观测**，
  且调用方必须能区分"投递"与"生效"。
- **控制类状态必须带归因**（谁、何时、为什么）。只报"停/跑"两种状态，等于把
  "agent 自己停的"和"人按的"混为一谈。
- **长跑里"没有新数据"本身就是一个事实**，页面必须显示它（否则静默失败看起来像正常运行）。
- 推论：**工具的"成功"若只等于"请求已发出"，就一定会诱发空转**——同一次长跑里，
  线路 100 被调车队 32 次、同一线路被重复退役 5–7 次（回执停在 `retire_unknown104`）。 这与 D39/D40（动作执行了、汇报丢了）是**同一类病的两个方向**。

### D53. 探针的假设也是探针条件：错的选择器凭空造出缺陷，还藏起了真缺陷（2026-09-23）

**现象**：修图表缩放时，我连续四次判定"缩放坏了"，其中**三次是我的仪器错**：

| 我断言的 | 实际情况 | 后果 |
|----------|----------|------|
| `document.querySelectorAll('.u-tick').length === 0` → "轴没有刻度" | uPlot **根本没有 `.u-tick` 这个类**（CSS/JS 里都不存在）；轴标签不在 DOM 里 | 我据此宣布"图表渲染坏了"，而截图显示刻度一直正常 |
| `UCharts.isZoomed(el) === false` → "缩放没生效/被回退" | 导出的 `isZoomed` 收的是**实例**，调用方按**元素**传 → **恒 false** | 四个探针（含冒烟脚本）读到的是同一个常数，不是状态 |
| `body.querySelector('.chart-ctrl')` → 点击"这张图"的按钮 | 命中的是**页面里另一张图**的按钮（文档顺序在前） | 点 A 图、量 B 图 → "按钮无效"，而按钮其实是好的 |

**根因**：我把"未经校准的选择器/API 假设"当成了判据，而且每次都先接受"产品坏了"这个结论。
真正存在的缺陷（`setScale` 不可依赖、`setData` 默认重置视野 —— 见 `SPEC.md` §10.97）是**最后**
才由**像素哈希**确认的：像素哈希是唯一与我的假设无关的证据（`＋`/滚轮 → 画面变了；`⟲` →
像素回到初始），它同时证明了"缺陷存在"与"修好了"。

**规则**：
1. **判据优先用用户能看见的东西**（像素哈希 / 截图 / 可见文本），DOM 与内部 API 只作辅助。
2. **探针必须自证可用**：先断言自己"认得目标"（例如先找到一处已知文本），
   拿不到就报 `instrument-error`，**不能报 `false`**——`false` 与"缺陷存在"无法区分。
3. **探针要双向自证**：在已知正常的路径上也要报 true（本轮 `⟲` 的 `restored: true` 就是这个作用）。
4. **跨边界传参必须有测试**：元素 vs 实例这类不兼容签名，要有一条"传错就 false"的用例。
5. 教训与 D48/D51 同源：**探针漏掉一个条件（dpr、窗口宽度、选择器、API 语义），
   验证就是空真**。D48 说"复现用户的条件"，D53 补上"先确认你的仪器真的在测量它"。

### D54. 数据量也是探针条件：17 行事件的页面量不出 200 行表格的成本（2026-09-24）

**现象**：用户报"~17k DOM 变更/秒"，我连续三次测量互相矛盾（10,548 / 290 / 数百）， 一度据此怀疑用户数字不可信。真相是：那几次探针跑在**刚开局的新局**上——
事件列表只有 **17 行**、步骤表还是空的；而用户的数字来自 **5.7 小时长局**
（两张 ~200 行表 + 高频推送）。

**换了可信仪器后（NaN-safe 累加 + 平行 WS 报帧率 + 在用户真实页面上跑）**：
**125,277 次节点操作 / 10 s = 12.5k/s，49 帧 → 2,557 变更/帧** ✓ 与用户报的 17k 同量级。

**规则**：
1. **测量前先检查"被测对象的规模"是否等于用户场景**（行数、帧率、局时长）。
   与 D48（窗口宽度）、D51（dpr）、D53（选择器/API 语义）并列：**数据量是同一类探针条件**。
2. **"每帧成本"与"帧率"必须分开报告**：上一次失败的根因就是没数帧，
   于是 12.5k/s 里分不清"帧多"还是"每帧贵"。
3. 规模不对时，正确动作是**换一个符合场景的被测对象**（长局/合成 200 行），
   而不是**用错规模的结果去质疑用户的观测**。

### D55. "面板是空的"先查通道，别查样式——同一模式已经发生三次（2026-09-25）

**现象**：用户报"线路/载具的详细面板是空的，明明有线路和载具"。我第一反应是查抽屉的 CSS/模板；实际形态查完是：抽屉与线路表**都正常**（13 行线路、8 行有车的线路），
而**城镇面板**是从未有过数据的——因为 `toWireSnapshot()` 没把 `snap.towns` 发出去。

**同一模式的第 1、2、3 次**：
1. `stats.breakdown {bus:9,…}`（车辆/站点类型分布）**一直在快照里**，只是没显示
   → "没有线路类型"是显示缺陷，不是数据缺陷（`SPEC.md` §10.96）。
2. `routes`：GS 一直在读数（`routeStats`），但**从没进过快照**（2026-09-23 修）。
3. `towns`：Bridge GS 一直在发 `town_list`，`world-state` 也存了，但 `toWireSnapshot` 丢掉
   （2026-09-25 修，`SPEC.md` §10.98）。

**根因**：后端"世界事实"与前端"页面事实"之间**没有契约**——两端各自手写字段名，
所以"后端加了、前端没接"可以**静默通过**：没有类型错误、没有控制台错误、没有测试失败，
页面只是**安静地空着**。而"空"在视觉上极容易被解释为"世界就是这样"。

**规则**：
1. **遇到"面板空"先问"这条数据到页面了吗"**：从**最上游**查起（GS/admin → world-state →
   `toWireSnapshot` → `onSnapshot` → 视图模型 → 模板），而不是从 CSS/模板查起。 本项目的空面板，三次里有三次是通道问题，零次是样式问题。
2. **新增一个后端事实 = 三件一起做**：① 类型（`world-state`/`toWireSnapshot`）
   ② 通道标志（`xxxAvailable`：区分"不可得"与"零"）③ 页面渲染 + 单测 + smoke 断言。
3. **取证方式**：用平行 WebSocket 直接读**服务端发出的快照**（而不是只读页面 DOM），
   这样能一次分清"后端没发"和"前端没渲染"（本轮就是这么定位的）。

### D56. 告警必须可行动：一句通用话把三种原因压成一种（2026-09-25）

**现象**：页面提示 "No decision for 1 hour… the process is alive but nothing is progressing"，
用户无法判断该做什么。取证后发现真相是**三种完全不同**的情况之一：

| 真实原因 | 证据 | 正确提示 | 该做什么 |
|---------|------|---------|---------|
| agent 自己按了暂停 | 快照 `control.pausedByAgent` | "Blocked — the agent paused the world itself (set_pause)" | 按 Resume |
| 模型/工具还在这一轮里 | agent step 很新，但没有新的游戏日 | "still inside a turn, not stalled" | 等 |
| 通道/进程死了 | 90 s 内**任何**事件都没有 | "no run data is arriving" | 查进程/日志 |

**根因（两层）**：
1. **诊断层**：我们只实现了"暂停了没有"这一个布尔量，缺"世界是否在推进""agent 是否还在动"
   "通道是否还在收数据"这三个**可独立取证**的判据，于是只能给出通用文案。
2. **状态层**：agent 的 `set_pause` 把归因写进快照，却**没写进 supervisor**（两个写者），
   页面读的是后者 ⇒ 归因被覆盖（详见 `SPEC.md` §10.101）。

**规则**：
1. **告警必须能落到一个动作上**（Resume / 等 / 查进程）。写不出动作的文案就是噪音，
   要么补判据、要么别显示。
2. **状态只有一个写者**。跨进程/跨层传递"谁做了什么"时，写者必须唯一；
   第二个写者（哪怕只是"顺手 publish 一下"）会在下一次正常同步时被覆盖，**真相静默丢失**。
3. **先取证再改**：本次先读 `audit.jsonl` 尾部才发现"agent 自己按了暂停"——如果直接从
   CSS/文案入手，会把一个状态归属 bug 修成一段更长的提示文字。

### D57 —— 订阅频率决定了事实的分辨率：`Monthly` 的通道不能当"当前时间"用

**现象**：页面 health 条长期显示 `WORLD frozen — no new game date in the last 90s`，
而事件流证明世界每 6 秒推进一次。agent 的 `observe` 也一直显示连接那一刻的日期。

**根因**：admin port 的 DATE 包是按 **`Monthly`** 订阅的（一局 90 s 只来 1 个），
而判据问的是"最近 90 s 内有没有新读数"。两个都对，接在一起就是一个**结构性**的假事实。
细粒度的读数一直在（GS 的 `GSDate`，每 200 tick ≈ 6 s），只是从没变成 `date` 事件。

**规则**：把一个通道当"当前状态"用之前，先问它的**刷新率**，并用真机事件计数复核
（一局里到底来了几个）。页面上任何"多久没有 X"的判据，X 的到达率必须比判据窗口**细**
一个数量级以上；否则它测的是订阅频率，不是世界。
与 D55（面板空 → 查通道）同源：**先确认事实真的在流**，再解释它为什么不对。

### D58 —— 临时探针与产品改动住在同一个文件里时，`git checkout` 会连产品一起 revert

**现象**：为验证 W3 往 `executor-ai/main.nut` 注入了一次性故障，跑完用
`git checkout -- <file>` 回退——**顺手把 worker 尚未提交的 W3 生产端实现也 revert 了**，
6 条 Squirrel 守卫当场变红。

**根因**：探针与产品改动同文件未提交；回退是文件级的，没有"只回退我加的那几行"。

**规则**：一次性探针要么放在**独立文件**里，要么在动手前先把产品改动
**提交或 stash**；必须同文件时，用精确的文本回退（`edit` 反向替换），不用文件级
`git checkout`。回退后立刻跑该文件的守卫——这次是守卫替我发现的，它没有白写。

### D59 —— 探针空跑：`ok=0` 什么也没证明（2026-09-26）

**现象**：API 探针要验 `GSVehicle.GetLastStation` 是否存在。探针对「公司车辆」循环调用它。 结果 `ok=0, err=""` —— 看起来像"失败且无错误信息"。实际上公司当时 **0 辆车**，
循环体一次都没执行。真实结论是「**未测**」，而探针报成了「失败」。

**根因**：探针没有证明自己的被测路径执行过。`D53` 说"假设是条件"，这条补另一半：
**"没跑到"与"跑不通"必须分开**。一个空转的探针会把「未知」伪装成「已知」。

**规则**：探针必须回报「实际测到的次数」（本例：迭代了几个对象）；
判读时先看 `tested>0` 才允许下结论。`ok=0 && tested=0` 的正确解读是「本次未测」，
换条件重测，**不写进 SPEC**（D43 的前置）。

### D60 —— 缺失折叠成 0，就是捏造事实（2026-09-26，探针实证）

**现象**：GS 里 `if (trans < 0) trans = 0;`，TS 里 `Number(x) || 0`。于是
`GetLastMonthTransported` 的 **-1**（"不适用/无此货种"）被层层折叠成「运了 0 吨」。
真机探针：一个采样期里 **548 个负读数**被折叠。用户看到整列 `Transported 0`，
并把它当真——那是捏造，不是观测。

**根因**：写解析的人默认"下游想要一个数字"。但 `null ≠ 0`（本仓库红线），
折叠发生在生产侧就没有任何测试看得见。这类折叠在事实链上每层都能发生
（`Number(x) || 0` / `?? 0` / Squirrel 侧 `if (x < 0)`），是仪表谎言最常见的一族。

**规则**：生产代码**不折叠缺失值**：缺席保持 `null`，页面显示 `—`。
`0` 只能来自"真的量到 0"。写解析器时对每个字段问一遍「缺失时下游会看到什么」。
新增字段的验收必须包含「缺失时显示 `—` 而不是 `0`」。
