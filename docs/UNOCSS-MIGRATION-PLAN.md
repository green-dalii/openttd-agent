# UnoCSS 迁移可行性评估与方案

> **职责**：本文件是"是否/如何引入 UnoCSS"这一主题的单一权威：实测数据、三个方案的取舍、
> 以及若推进时的分阶段方案与验收。
> **边界**：候选库的通用事实矩阵与 D3（"无构建链"）的澄清在
> `docs/FRONTEND-LIBRARY-EVALUATION.md`；本文件只回答 **UnoCSS 这一个决定**并给出数字。
> 规则条文在 `AGENTS.md`；"谁能改 D3"由所有者决定（§6）。

## 0. 结论（先给答案）

1. **不采用 runtime 模式**（`@unocss/runtime`）：不是因为它慢（实测很便宜，见 §1），
   而是**载荷账算不过来**——它给一个 **10.8 KB gz** 的 CSS 预算再**加 51.5 KB gz**（+4.8×），
   而它最多能替代的那部分样式只值 **约 20% 的 `style.css`**。
2. **若未来仍要引入 UnoCSS，唯一合理形态是 CLI 模式 + 提交产物 + 门禁校验**
   （"生成但被验证"：改源忘了生成 → **门禁红**，而不是页面静默变旧）。理由见 §3。
3. **当前不建议做整站迁移**：可替代比例小（§2）、`style.css` 是五页共享文件（搬进 markup
   会丢掉共享摊薄）、现有小词汇表（`dim`×63、`num`×46、`panel`×24…）**已经在做 utility 该做的事**。
4. 真要推进 → §5 的**单页试点**先行，验收用同一套探针（载荷、类数、style.css 缩减、控制台）。

## 1. 实测：runtime 模式的真实成本（2026-09-24，跑在真实运行中的 dashboard 上）

方法：同一页面、同一批 DOM 突发（200 个元素 × 20 个 utility 类，插入→移除），
**分别在有/无 `uno.global.js`（v66.10.5，npm 包字节）时各测 7 次取中位**；
另开一条平行 WebSocket 数**真实推送帧数**（把"每帧成本"与"帧率"分开——
这正是上一轮测量失败的根因）。

| 指标 | 无 runtime | 有 runtime | 结论 |
|------|-----------|-----------|------|
| 突发耗时（中位） | **0.70 ms** | **1.20 ms** | 重扫开销 **+0.5 ms / 200 元素**（≈0.0025 ms/元素） |
| CSS 规则数 | 320 | 347 | 只增加**被用到**的生成项 |
| 实时 10 s 窗口（runtime 在场） | — | 规则增量 **0**；长任务 **1 次 / 57 ms** | **没有** "每次 DOM 变更重算 CSS" 的迹象 |
| 实时窗口的页面变更 | — | **125,277 次节点操作 / 10 s = 12.5k/s**，49 帧 | 与用户报的 ~17k/s 同量级 ✓ |

**因此"runtime 有 #4766 风险"这条早先的担忧，在 66.10.5 上未被复现**：
重扫便宜、且不重算已生成的规则。**否决 runtime 的理由是载荷，不是速度。**

**同时修正上一轮的一个测量错误**：当时在新局（仅 17 行事件）测得"稳态只有几百/10s"，
据此怀疑 churn 很小——那是**低数据量下的假阴性**。真实长局的数字是
**2,557 次变更/帧 × 4.9 帧/s = 12.5k/s**（见 `ROADMAP.md` §6c）。

## 2. 实测：可替代比例（决定 payoff 上限）

对 `pages/*.html`、`assets/js/*.js`（含 `className=` / `classList.*` 字面量）与
`assets/css/style.css` 做交叉统计：

| 项 | 数值 | 含义 |
|----|------|------|
| HTML/JS 引用的类名 | **160** | 语义组件类为主 |
| `style.css` 单类规则 | **114 条 / 11,046 字节**（规则体） | 只有这部分**可能**被 utility 表达 |
| ├ 被复用 ≥5 次（真组件，**保留**） | **16 条 (15%)** | 如 `dim`×63、`num`×46、`panel`×24、`kpi`×16 |
| ├ 被用 ≤1 次（**可内联为 utility**） | **78 条 (67%)** | 主要是 `act-*`/`cbx-*`/`arm-*` 这类一次性结构 |
| └ 本次扫描未引用 | 24 条 (14%) | **未证明是死代码**（可能在 `index.html`/动态构造里），需人工确认 |
| 状态 / 后代 / 属性选择器规则 | **~180 条** | utility **无法表达**，必须留在 CSS 里 |

**上限**：可替代部分 ≈ **style.css 的 20%**。而且它与 `style.css` 的
**共享摊薄**相冲突——`style.css` 是**五页共用的一个文件**（10.8 KB gz 摊到 5 页），
把样式搬进各页 markup 意味着**每个页面各自付一次**。

## 3. 三个方案对比

| 方案 | 载荷 | 工具链 | 静默失败面 | 判定 |
|------|------|--------|-----------|------|
| **A. 不迁移**（现状） | baseline | 无 | 无 | ✅ **推荐**（除非 §5 的试点证明有净收益） |
| **B. runtime**（`uno.global.js` 直接引入） | **+51.5 KB gz**，是可达节省(≈2.2 KB gz)的 **23×** | 无（字节级 vendor ✅） | JS 动态构造的 **22 个类名**要等重扫才生效 → 这些组件首次出现会**闪一下**（FOUC） | ❌ **否决**（载荷） |
| **C. CLI + 提交产物 + 门禁校验** | 只含**实际用到**的 utilities（预计 1–3 KB gz） | 需要一个**生成步骤** | 若忘了生成 → **门禁红**（见下），不是静默变旧 | ⚠️ **唯一可能划算的形态**；需所有者放行 D3(b) |

**方案 C 为什么能绕开 D3 的本意**：D3"无构建链"的真实载荷是
*"磁盘上跑的就是仓库里的" + "没有会被忘记的生成步骤"*（见 `docs/FRONTEND-LIBRARY-EVALUATION.md` §2）。
把 `uno.css` **提交进仓库**、并加一条门禁命令"重新生成到临时文件 + 字节比对"
（与现有 `scripts/verify-vendor.ts` 同一模式），就同时满足两点：
忘了生成 = **门禁失败**，而不是页面静默用旧样式。**代价**是必须放弃"零工具链"，
所以**需要所有者决定**（`FRONTEND-LIBRARY-EVALUATION.md` §5 的 A/B 二选一）。

## 4. 若选 C：风险清单（先钉死，再动手）

1. **JS 构造的类名（22 处）**：`toast ${kind}`、`cbx*`、`modal`、`chart-tip` 等。
   UnoCSS 的 CLI 抽取是**文本级**的，字面量 `"toast info"`／模板串里的 `cbx` 能命中，
   但**拼接出来**的（如 `'k'+i`）不能 → 必须 **safelist**，并加一条测试断言
   "所有 JS 构造的类名都在生成的 `uno.css` 里"。
2. **FOUC**：CLI 模式生成的是静态文件，不存在 runtime 的重扫延迟 ✓。
3. **令牌漂移**：现有 **39 个 CSS 变量**必须成为 UnoCSS `theme` 的**唯一来源**
   （从 `style.css` 读取生成，或反向：以 theme 为源生成 CSS 变量）——
   否则会出现"两套颜色/间距各改一半"的漂移。
4. **不要动状态/后代规则（~180 条）**：utility 表达不了，强行改写会破坏
   `:hover`/`:focus-visible`/`[hidden]`/`::before` 等语义与可访问性。
5. **改变共享摊薄**：把共享 CSS 搬进 markup 会让**每页**都更大 → 试点必须**逐页量载荷**。

## 5. 若推进：分阶段方案与验收（单页试点优先）

| 阶段 | 做什么 | 验收（可执行） |
|------|--------|----------------|
| **U0 试点（一页）** | 选 **Providers 页**（最小、无图表）：接入方案 C，把该页 ≤1 次使用的类改为 utility | ① 该页 gz 载荷**不增**（对比 `Content-Length`）② `pnpm run dashboard:smoke` 绿（全部控制台级别 + 有数据状态）③ 人工逐个交互点一遍（AGENTS §5.2.4） |
| **U1 令牌统一** | 39 个 CSS 变量成为 theme 单一来源 | 单测：`style.css` 的变量与 theme **双向一致**（改一处即红） |
| **U2 逐页替换** | 只动"≤1 次使用"的规则；组件类（≥5 次）不动 | 每页：`style.css` 缩减字节 > 该页新增 utility 字节；§5.2 全绿 |
| **U3 门禁化** | `pnpm run uno:check`（重新生成 + 字节比对）进 `gate` | 故意改一处标记 → 门禁**必须变红**（守卫自证，见 MEMORY D49/D53） |
| **停止规则** | 任一页出现载荷增加或 0 net 缩减 → 停下，保留现状 | 记录实测，不在 ROADMAP 留"半迁移"状态 |

## 6. 需要所有者决定的一件事

- **D3(b) 是否放行**（即方案 C 需要一次生成步骤）：
  - 放行 → 按 §5 从 **U0 单页试点**开始，用实测决定是否继续。
  - 不放行 → **保持现状（方案 A）**；若只是想要"新代码写得更快"，
    成本更低的替代是：把现有 39 个变量 + 少量高频类当作既有词汇表用（无需任何工具链）。
- 无论哪种，**runtime 模式都不建议**（§0/§3 的载荷账与 22 处 JS 类名的 FOUC）。
