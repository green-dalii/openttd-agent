# 前端库评估与 D3（"无构建链"）的澄清

> **职责**：本文件是**前端第三方库取舍**这一主题的单一深入说明：候选库的事实矩阵、
> UnoCSS 的可行性判定、以及"无构建链"这条规则到底约束什么 + 需要所有者决定什么。
> **边界**：规则条文在 `AGENTS.md`；已采用的依赖与其审计在 `docs/FRONTEND-DEPENDENCIES-AUDIT.md`；
> 图表交互的**系统事实**在 `SPEC.md` §10.97；本文件不重复它们的结论，只做指针。

## 1. 为什么会有这份文档

所有者在评审前端时提出用 **UnoCSS** 取代手写 CSS。要回答"行不行"，先得回答
"现在的规则到底禁止什么"——因为现行的 **D3（"前端无构建链"）** 从没有被写清它的**成本与收益**，
于是后续讨论里**两个不同的约束被混成了一个**。

## 2. 被混在一起的两条约束（证据）

| 约束 | 到底是什么 | 有无正当理由 | 违反后的真实代价 |
|------|------------|--------------|------------------|
| **(a) 离线 / 不用 CDN** | 产物必须落在仓库里、`file:`/本地服务即可运行 | **硬约束**，有理由：无网络环境、可复现、审计 | 引入 CDN 依赖 → 离线即坏；已被 `scripts/verify-vendor.ts` + `test/unit/vendor.test.ts`（字节级）守住 |
| **(b) 无构建链** | 不允许"源码 → 产物"的生成步骤 | **偏好**，其**真实载荷**是三点：*磁盘上跑的就是仓库里的*、*没有会被忘记的生成步骤*、*零工具链* | 需要一个 generate 步骤 + 产物会过期（改了源、忘了生成 → 页面跑的是旧的），这类"陈旧产物"是**新的静默失败面** |

来源：`D3` 是 v0.0.1（`f61b8ba`）里的一行决定，**没有记录成本/收益分析**；
而 D3 **已经被放宽过一次**——Alpine.js 是所有者推动后引入的（见
`docs/FRONTEND-DEPENDENCIES-AUDIT.md` §3）。也就是说"无构建链"一直按**惯例**执行，
而不是按一条被论证过的规则执行。

**结论**：(a) 必须保留，(b) 需要所有者明确。建议的措辞见 §5。

## 3. 候选库事实矩阵（2026-09-23 核对）

| 库 / 方案 | 体积 | 许可 | 需要生成步骤？ | 可字节级 vendor？ | 对本项目的判定 |
|-----------|------|------|----------------|-------------------|----------------|
| **uPlot 1.6.32**（已用） | 51 KB min | MIT | 否 | ✅ 已在 `assets/vendor/uplot/` + `PROVENANCE.json` | 保留（交互已自实现并**像素级验证**，见 `SPEC.md` §10.97） |
| **Alpine.js**（已用） | ~44 KB min | MIT | 否 | ✅ 已 vendored | 保留 |
| **Lightweight Charts v5** | 35 KB（base） | Apache-2.0 | 否（`lightweight-charts.standalone.production.js` 是 IIFE） | ✅ | **可**作为 uPlot 的替代：自带滚轮/双指缩放、拖拽平移、缩放工具条、十字光标。但**只有在**"原生交互 + 十字光标"胜过我们已修的适配层时才值得换（换 = 重写已验收的 4 项交互） |
| **Web Awesome**（Shoelace 的继任者；Shoelace 已 sunset） | 按组件加载 | MIT | 否（预构建 dist） | ✅ | 需要表单/对话框类**组件**时可选；现在没有这个需求 |
| **Open Props** | tokens（CSS 变量） | MIT | 否 | ✅ | 只提供设计令牌；若想给 `style.css` 的变量一个来源可以用，收益有限 |
| **Preact + htm** | 8 KB + <600 B | MIT | 否（htm 不需要转译器） | ✅ | 只有当 DOM 更新成为瓶颈时才有意义（见 `ROADMAP.md` §6c 的实测：问题是**吞吐**，不是渲染器） |
| **Pico CSS** | 12 KB gz | MIT | 否 | ✅ | ✗ 类无样式（classless）会与本项目已有的大量定制 CSS 打架 |
| **Tailwind v4**（standalone CLI） | 按用量 | MIT | **是**（生成 `output.css`） | 产物可 vendor，但**源→产物**这一步违反 (b) | ✗（除非按 §5 改成 B） |
| **Vue / React（SFC）** | — | — | **是**（转译器） | ✗ | ✗ |
| **UnoCSS（runtime 模式）** | `uno.global.js` 183 KB raw / **50 KB gz** | MIT | 否 | ✅ | ⚠️ **有实测风险**，见 §4 |
| **UnoCSS（CLI 模式）** | 生成的 `uno.css` 按用量 | MIT | **是** | 产物可 vendor | ⚠️ 违反 (b) 的"无生成步骤"，收益是静态 CSS |

（`uPlot.iife.min.js` / `uPlot.min.css` 与 npm 包**字节一致**，由 `scripts/verify-vendor.ts` 把关；
`PROVENANCE.json` 是审计台账。）

## 4. UnoCSS 的可行性判定（有数字，不是印象）

- **runtime 模式**（`@unocss/runtime`）：在浏览器里扫描 class 并按需生成规则。
  已知缺陷 **issue #4766：每次 DOM 变更都会触发重新扫描/重算 CSS**。
  本项目**恰好**踩在这条上：页面在遥测帧下持续产生**元素增删**级别的 DOM 变更
  （合成最坏情况 1,806–2,606 次/更新；真实页面的稳态量级仍**没有可信数字**——
  见 `ROADMAP.md` §6c 对三次互相矛盾的测量的记录）。
  把"每次变更都重扫"的库放进这个页面，等于给已经最热的那条路径再加一层放大器。
  ⇒ **默认不采纳**；若要用，必须先做一次**有界实验**并给出数字（见下）。
- **CLI 模式**：生成的 `uno.css` 是静态产物，运行时零开销；代价是**多一个生成步骤**
  （改了模板忘了生成 → 页面样式静默变旧）。这与 (b) 的"没有会被忘记的生成步骤"直接冲突。

**有界实验（若所有者想推进）**：vendored `uno.global.js` + 在页探针，量
**每秒 CSS 规则变更/样式重算次数**，**必须同时报告遥测帧率**（否则和 §6c 一样无法归因）；
接受门槛：在真实推送率下**无可测的样式抖动**（对照：修好之前的图表高度抖动是"每帧乘 dpr"，
那种量级必须能被抓到）。达不到门槛 → 选 CLI 模式（代价：生成步骤），或不用。

## 5. 需要所有者决定的一件事（A / B）

- **A（建议）——澄清 D3，不动产物机制**：
  > 允许 **vendored 预构建第三方产物**（带 `PROVENANCE.json` 与字节级校验）；
  > **禁止第一方源码 → 产物的生成步骤**（这才是"会被忘记的生成步骤"的来源）。
  在此规则下：Lightweight Charts / Web Awesome / Open Props / vendored UnoCSS **都允许**；
  Tailwind CLI / Vue / React SFC **不允许**（它们要转译**第一方**源码）。
- **B——正式把 (b) 也放开**：允许前端构建链（Vite + 任一 CSS 框架）。
  代价要在提交信息里写清：多一个工具链、产物会陈旧、CI 与本地都要生成一次。

（A 与 B 的分界不是"能不能用库"，而是**"产物是不是仓库里就有"**。）

## 6. 若选 A：推荐的推进顺序（只在能删掉手写代码时才引入）

1. **不动**：Alpine + uPlot 保持现状——图表交互刚修好并做了像素级验证
   （`SPEC.md` §10.97），此时换库 = 重写已验收的东西，没有量到的收益。
2. **Open Props**（可选）：只在打算给 CSS 变量一个统一来源时引入。
3. **Web Awesome**（按需）：出现真正的表单/对话框组件需求时引入。
4. **Lightweight Charts**（条件性）：当且仅当"原生十字光标 + 原生缩放工具条"
   被判定为**用户可见的收益**时，作为 uPlot 的替代品引入，并保留现有的
   "图表健康"断言（宿主高度、像素稳定性）。
5. **UnoCSS**：先按 §4 的**有界实验**拿数字，再决定 runtime / CLI / 不用。
